# CLAUDE.md

Book&Plan: веб-платформа поиска и бронирования ресурсов трех доменов в одной системе.
Файл объединяет выжимку PRD и стандарты разработки команды (Project Standards, Taiga Wiki).
Стандарты являются правилами по умолчанию. Они меняются только явным решением команды с фиксацией изменения.

## Архитектура

- Один репозиторий, модульный монолит, один deployable backend. Микросервисы в MVP не используются.
- Backend следует [HackSoft Django Styleguide](https://github.com/HackSoftware/Django-Styleguide).
- Дополнительные слои и абстракции добавляются только при конкретной технической необходимости.
- Доменные модули разделены: `university`, `restaurants`, `hotels`. Общая booking-логика живет в `bookings`.
- Цепочка всех доменов: Authentication → Search → Availability → Booking → Cancellation → Administration.

### Правила HackSoft

1. Бизнес-логика живет в services и selectors. APIs, serializers, admin и signals ее не содержат.
2. Service: функция `<entity>_<action>` (`booking_create`, `booking_cancel`), только keyword-only аргументы, type hints. Перед `save()` вызывает `full_clean()`. Несколько записей оборачивает в `transaction.atomic`.
3. Selector: функция `<entity>_list` или `<entity>_get`, только чтение, возвращает QuerySet или объект.
4. API: класс `<Entity><Action>Api` (`BookingCreateApi`) на основе `APIView`. Вложенные `InputSerializer` и `OutputSerializer`. Вызывает один service или selector.
5. Модель наследует `apps.common.models.BaseModel`. Choices объявляются как `models.TextChoices` в `models.py` своего app.
6. Инварианты одной таблицы держат `Meta.constraints`. `full_clean()` проверяет их до записи. Проверки через связи (`guests <= resource.capacity`) делает service.
7. URL app описаны в `apps/<app>/urls.py` и подключаются в `config/urls.py` под `/api/v1/`.
8. Настройки интеграций (CORS, Celery, Sentry) получают отдельный файл `config/settings/<name>.py`, когда интеграция появляется.
9. Settings читают переменные окружения через `env` из `config/env.py` (django-environ). `config/django/base.py` подгружает `.env` из корня репозитория. Переменные окружения процесса важнее файла: Docker Compose подменяет `POSTGRES_HOST=db`.

### Детали Django

- `AUTH_USER_MODEL = "accounts.User"` задан до первого `migrate`. Замена модели позже требует пересоздания БД.
- `Role` (`CLIENT`, `MANAGER`, `ADMIN`) объявлен в `apps/accounts/models.py`.
- `bookings` хранит `Resource` (вид, название, вместимость, активность, менеджер) и `Booking` (ресурс, клиент, начало, конец, число гостей, статус).
- Будущие модели `Room`, `Table`, `HotelRoom` ссылаются на `Resource` через `OneToOneField`. Один exclusion constraint на `Booking` закрывает конфликты всех трех доменов.
- Период отеля хранится от полуночи даты заезда до полуночи даты выезда.
- `booking_create` ловит `IntegrityError` от `booking_no_overlap` и возвращает ошибку `BOOKING_CONFLICT` с HTTP 409.
- ADM-001..ADM-006 закрывает Django admin через `admin.py` каждого app.
- Тесты идут на PostgreSQL: SQLite не поддерживает exclusion constraint. Тест гонки бронирований использует `TransactionTestCase` и два потока.

## Стандарты кода

### Python / Django

- PEP 8, отступ 4 пробела.
- Black форматирует код, Flake8 проверяет lint (`backend/.flake8`). Длина строки 100, `migrations/` исключены из обоих.
- Файлы, функции и переменные в `snake_case`, классы в `PascalCase`, константы в `UPPER_SNAKE_CASE`.
- Логические переменные читаются как вопрос: `is_active`, `has_access`, `can_cancel`.
- Публичные функции и services получают type hints.
- `django-stubs` (dev-зависимость) дает IDE и type checkers типы Django: поля моделей, `TextChoices` с подписями, admin.
- Бизнес-правила проверяются на backend. Большие файлы делятся.

### React / TypeScript

- ESLint и Prettier.
- Компоненты в `PascalCase`, функции и переменные в `camelCase`, hooks `useSomething`.
- Логические переменные: `isLoading`, `hasError`, `canBook`.

### Комментарии в коде

- Каждый класс, функция и метод получает docstring на русском.
- Docstring начинается с «Класс, ...», «Функция, ...» или «Метод, ...» и причастия: «Класс, описывающий бронь ресурса». Точка в конце не ставится.
- Текст понятен человеку без знания Django.
- Строчные комментарии `#` в коде не используются.
- Сгенерированные миграции docstring не получают.

## API

- Префикс `/api/v1/`. Ресурсы называются существительными во множественном числе: `/bookings/`, `/hotels/`.
- Стандартные HTTP-методы и status codes.
- Backend валидирует вход независимо от frontend.
- Единый формат ошибки:

```json
{
  "code": "BOOKING_CONFLICT",
  "message": "The selected resource is not available.",
  "details": {}
}
```

## База данных

- PostgreSQL хранит все постоянные данные.
- Каждое изменение схемы идет через migration. Ручные изменения БД в обычной работе запрещены.
- Реальные инварианты держат database constraints и foreign keys.
- Доменные сущности имеют `created_at` и `updated_at` через `BaseModel`.
- Секреты в открытом виде не хранятся.

## Git workflow

| Ветка | Назначение | Правила |
|---|---|---|
| `main` | Production-ready код, deployment в production | Защищена, прямой push запрещен, PR только из `dev` или `hotfix/*`, CI зеленый, минимум 1 reviewer |
| `dev` | Текущая интеграция | Защищена, прямой push запрещен, PR из feature/fix-веток, CI зеленый |

- Обычный путь: `dev` → feature/fix-ветка → PR → review + CI → `dev` → PR → `main`.
- Feature/fix-ветки не сливаются в `main` напрямую.
- Hotfix: `main` → `hotfix/TG-999-critical-error` → PR → `main`. После выпуска изменение переносится в `dev`.
- Squash merge по умолчанию. Ветка удаляется после merge. Ветка `develop` не создается.
- Сейчас на GitHub ветка `master` вместо `main`. Ее нужно переименовать в `main`.

Имена веток: `<тип>/TG-<номер задачи Taiga>-<описание в kebab-case>`.

```
feature/TG-123-booking-availability
bugfix/TG-245-double-booking
docs/TG-310-api-documentation
chore/TG-401-update-ci
hotfix/TG-999-critical-error
```

## Pull Requests

- Название в формате коммита: `feat(booking): add availability endpoint TG-123`.
- Описание: ссылка на Taiga item, кратко о задаче, что изменено, как проверено, screenshots для заметных изменений UI.
- Минимум 1 reviewer.
- Review Team Lead обязателен для: архитектуры, основной логики бронирования, структуры БД, authentication и authorization, CI/CD.

Reviewer проверяет: задача Taiga решена, Acceptance Criteria выполнены, код понятен, стандарты соблюдены, бизнес-правила проверяются на backend, нужные тесты есть, ошибки обработаны, безопасность не нарушена, документация обновлена.

## Тестирование

- Обязательные автотесты: предотвращение двойного бронирования, permissions, создание брони, отмена брони, расчет доступности.
- Backend: pytest и pytest-django. Frontend: Vitest и React Testing Library.
- Процент coverage не является целью. Тесты покрывают важное поведение и критические бизнес-правила.
- QA проверяет Story вручную перед переводом в Done.

## Ошибки и логирование

- Ошибки не игнорируются молча. API возвращает контролируемые ошибки в едином формате.
- Неожиданные ошибки backend пишутся в logs.
- Stack traces и секреты не попадают к пользователю.
- Пароли, tokens и чувствительные данные не пишутся в logs.
- Frontend показывает понятные состояния ошибок.

## Definition of Ready

Story готова к работе, если: понятна ценность, определены Acceptance Criteria, известны зависимости, основные вопросы решены, команда может оценить работу, Story помещается в спринт.

## Definition of Done

Story считается Done, если: реализация завершена, Acceptance Criteria выполнены, стандарты соблюдены, PR прошел review и merged, тесты проходят, QA проверил, критических дефектов нет, документация обновлена, статус в Taiga обновлен.

## Работа с AI

- Secrets и private data не передаются в AI, в код, в коммиты и в промпты.
- Предложенные библиотеки и API проверяются на существование и актуальность версии.
- AI-код проходит обычный code review. Разработчик отвечает за корректность, архитектуру, безопасность и тесты.
- «Это сгенерировал AI» не является основанием для merge.

## Статусы бронирования

| Статус | Значение |
|---|---|
| `CONFIRMED` | Бронирование создано и действует |
| `CANCELLED` | Бронирование отменено |
| `COMPLETED` | Период использования ресурса завершен |

Бронирование хранит статус, время создания и время изменения (FR-010).
Университетская бронь получает `CONFIRMED` автоматически после проверки доступности (UNI-007).

## Бизнес-правила

Все правила проверяет backend. Проверка на frontend нужна только для UX.

1. Два пересекающихся `CONFIRMED` бронирования одного ресурса запрещены.
2. Создать бронирование может только аутентифицированный пользователь.
3. Клиент изменяет и отменяет только собственные бронирования.
4. Менеджер управляет только закрепленными за ним ресурсами.
5. Административные операции доступны только администратору.
6. Дата и время бронирования лежат внутри периода доступности ресурса.
7. Число гостей не превышает вместимость столика или номера.
8. Отель: дата выезда строго позже даты заезда.
9. Создание бронирования атомарно: конкурентные запросы не дают двойного бронирования (NFR-003).

Правила 1, 8 и 9 держат constraints в `backend/apps/bookings/models.py`:

- `booking_no_overlap` (`ExclusionConstraint`) запрещает пересечение броней одного ресурса со статусом, отличным от `CANCELLED`. Расширение `btree_gist` включает миграция `bookings 0001`.
- Ограничение в БД отклоняет гонку, которую пропускает проверка "SELECT, затем INSERT" в коде.
- Период полуоткрытый `[start_at, end_at)`: бронь с 10:00 до 12:00 не конфликтует с бронью с 12:00 до 14:00.
- `booking_end_after_start` требует `end_at > start_at`.
- Правило 7 (`guests <= capacity`) проверяет service `booking_create`: CHECK в PostgreSQL не читает другую таблицу.
- Тесты правил: `backend/apps/bookings/tests/models/test_booking.py`.

## Границы MVP

Входит: аутентификация и роли, три booking-модуля, каталог с поиском и фильтрацией, проверка доступности, создание, просмотр и отмена бронирований, менеджерский интерфейс, административный интерфейс, тесты критических правил, Docker Compose, базовый CI.

Не входит, не реализовывать:

- онлайн-платежи и возвраты;
- рекомендательные системы;
- динамическое ценообразование;
- программы лояльности;
- карты и геолокация;
- внешние production-интеграции;
- нативные мобильные приложения;
- мультиязычность;
- продвинутая аналитика и BI;
- полноценная система уведомлений;
- AI-функции;
- отдельный модуль планирования мероприятий.

Данные в MVP тестовые и демонстрационные.

## Критерии готовности MVP

| Сценарий | Критерий |
|---|---|
| Университет | Найти помещение → проверить доступность → забронировать → увидеть бронь → отменить |
| Ресторан | Выбрать ресторан, дату, время и число гостей → выбрать доступный столик → забронировать → увидеть бронь |
| Отель | Выбрать отель и даты → увидеть доступное размещение → забронировать → увидеть бронь |
| Менеджер | Создать и отредактировать свой ресурс, просмотреть его бронирования |
| Администратор | Управлять пользователями и ресурсами платформы |
| Инженерная готовность | Запуск через Docker Compose; PR проходит CI; критические booking-правила покрыты тестами |

PRD не задает эти детали. Решение фиксировать в Product Backlog до реализации.

- FR-009: сроки и условия отмены брони.

- Покрывает ли Django admin административный интерфейс из PRD или нужен свой UI.
